## 2. Dashboard "Tool calls → Web searches"

- **[Verified, Meta docs fetched 2026-10-30]** Meta's tool-calling guide says: "This page covers developer-defined tools: functions you describe in tools and execute in your own code. The API also offers two built-in tools that run server-side: web_search … and tool_search." It also says: "The model does not execute developer-defined tools itself. Your app handles execution for every tool you define in tools."
- **[Verified, same date]** The pricing page bills "Web search grounding: $2.50 per 1,000 search queries … This applies to the web_search tool on text models such as Muse Wonder and Muse Spark."
- **[Inference, not confirmed by Meta documentation]** Meta's docs don't define the dashboard's "Tool calls → Web searches" counter. From the API docs and the pricing page, it most likely counts queries made by the server-side `web_search` tool, which this project never sends, so a value of 0 is consistent with our code. Our nine function tools (`list_documents`, `record_fact`, `verify_booking` and so on) run in our own code. On this reading they appear as ordinary requests and tokens rather than as web searches, but no documentation we found confirms how, or whether, the dashboard counts developer-defined tool calls.
- **[Inference]** "Images 0": on the pricing page, images are a billing unit for Muse Image generation ($0.01 per generated image) and SAM segmentation. Reading the appointment card with Muse Spark is billed as input tokens, so it shouldn't appear as an image. This entry generates no images and runs no segmentation.

## 4. Real code, real feedback; model-chosen vs fixed

**[Verified, code reading 2026-10-30, `harvey_agent/loop.py:70–150`]**

1. Each live turn calls `api.responses.create(model=muse-spark-1.3, input=record['messages'], tools=tools.definitions(...))`.
2. The model's `function_call` is passed to `tools.run(...)` (`agent_kit/tools/__init__.py:63`). That function runs real Python: it reads files, matches quotes exactly, and recomputes the fare and curb checks through `evidence.inspect`.
3. The result is appended as `{"type": "function_call_output", "call_id": …, "output": json.dumps(result)}` to the conversation the model sees on its next turn.
4. If the model asks for card images, they are attached as `input_image` content.
5. Refusals (for example, "Quote must occur exactly in a source document read in this run") go back the same way, so the model can correct itself.

| Model-selected (live mode) | Fixed by code |
|---|---|
| Which tool to call each turn, and its arguments | Transcription runs before the review, only after the rider clicks Record and confirms the transcript |
| The checklist questions, plan, document choice and quotes | Tool argument schemas, and the rule of exactly one tool per turn |
| When to verify, request evidence or submit a memo, and the memo text | Fare, curb, intake, card, spoken-request and counter-evidence checks: the model can't change their outcome |
| | The memo is accepted only after `verify_booking` on unchanged evidence, with an exact-quote citation per item |
| | Final states (`needs_input` / `awaiting_signoff`), the human sign-off, dispatch kept off, and the integrity check |

Offline simulation is a different path. A fixed script (`_simulation_calls`) supplies the tool choices, and no model is called. It's labeled **OFFLINE SIMULATION — NO META API CALLS** in the console and `DETERMINISTIC_FALLBACK_SIMULATION` in the record.
